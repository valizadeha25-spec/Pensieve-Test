# Systems

PamAI's systems estate separates structured project state from persistent work context, both on Supabase, and runs an AI request path, integrations, and supporting services around them.[^\[1\]^](https://app.pensieve.uk/r/506/data/186) [^\[2\]^](https://app.pensieve.uk/r/506/data/9) The three main systems are [Product Architecture](./product-architecture/page.md) for the product's data foundation, [Company Brain](./company-brain/page.md) for layered internal context, and [Network OS](./network-os/page.md) for operational relationship records.

## How the estate fits together

The product separates project information into two durable substrates: structured work and execution state lives in Supabase Postgres, with the Drizzle schema as the code-level source of truth,[^\[3\]^](https://app.pensieve.uk/r/506/data/186) while rich context lives as files in Supabase Object Storage, primarily in the private `agent-files` bucket.[^\[4\]^](https://app.pensieve.uk/r/506/data/186) Foundation holds the concise canonical foundation in `project.md`,[^\[5\]^](https://app.pensieve.uk/r/506/data/187) and Planning reads it and writes Fronts, Milestones, Batches, and Items into Postgres — current behavior whose long-term status is explicitly unresolved.[^\[6\]^](https://app.pensieve.uk/r/506/data/187)[^\[7\]^](https://app.pensieve.uk/r/506/data/186)

Web and Desktop do not own separate project models: Postgres remains authoritative for structured project data on both surfaces, Object Storage remains the durable cloud source for files, and Desktop SQLite stores Desktop operational state rather than acting as a second structured project database.[^\[8\]^](https://app.pensieve.uk/r/506/data/186) Routing between the substrates is currently enforced mainly through agent instructions and skills, not through one universal data abstraction.[^\[9\]^](https://app.pensieve.uk/r/506/data/186) The separation was chosen before the team had its practical Company Brain experience and is a current implementation choice, not a proven final answer.[^\[10\]^](https://app.pensieve.uk/r/506/data/186) Detailed storage boundaries, runtime authority, and the remaining architecture questions are maintained in [Product Architecture](./product-architecture/page.md).

## Context and operational systems

[Company Brain](./company-brain/page.md) is Pam's internal AI work-context system. Its working taxonomy treats `CLAUDE.md` and `RESOLVER.md` as the most fundamental, roughly always-loaded layer, scopes `domains/<x>/` to cases and areas and skills files to capabilities, keeps tracked and queryable state in database rows rather than the filesystem, and holds `memory/` as provisional material that can be promoted to more fundamental layers when it proves durable.[^\[11\]^](https://app.pensieve.uk/r/506/data/31) Its child page, [Content Library](./company-brain/content-library/page.md), maintains the persistent content-research corpus.

[Network OS](./network-os/page.md) is the operational network system. It lives in Supabase and is surfaced through the existing Company Brain dashboard and agent tools; its database is the canonical operational record, and a person's profile or timeline is not mirrored into Markdown.[^\[12\]^](https://app.pensieve.uk/r/506/data/50) Its child page, [LinkedIn Connection Operations](./network-os/linkedin-connection-operations/page.md), controls LinkedIn connection execution.

## AI request path, integrations, and services

PamAI sends user content to AI models through the Vercel AI Gateway.[^\[13\]^](https://app.pensieve.uk/r/506/data/9) By default, AI requests are configured for Zero Data Retention, so providers do not retain prompts or outputs after a request is served; provider pinning restricts inference to a vetted allowlist of US/EU or Western/GDPR-aligned hosts, and a request fails rather than routing to a host outside that allowlist; and provider training on interactive conversation data is an explicit profile setting that is off by default.[^\[14\]^](https://app.pensieve.uk/r/506/data/9)

PamAI stores and retrieves workspaces, projects, messages, files, and memory, and runs user-requested integrations and imports.[^\[15\]^](https://app.pensieve.uk/r/506/data/9) The documented integration surface covers Telegram, WhatsApp, Google Calendar, Notion, ClickUp, and coding-agent client data, and the listed subprocessor categories include hosting, storage, authentication, AI inference, messaging, email, sandbox compute, error monitoring, and payment providers.[^\[16\]^](https://app.pensieve.uk/r/506/data/9) See [Privacy & Data Protection](../privacy-data-protection/page.md) for personal-data governance and provider-specific handling, and [Product](../product/page.md) for the user-facing workflows these systems serve.

## Architecture status and boundaries

Current claims about PAM's implementation must be grounded in Amir's direct account and the current PAM codebase; current implementation, current assumptions, and possible redesigns remain visibly separate, and an ontology brainstorm does not authorize a schema, storage, or business-logic decision.[^\[17\]^](https://app.pensieve.uk/r/506/data/184) The current architecture record is explicitly current-state technical grounding, not a future architecture proposal.[^\[18\]^](https://app.pensieve.uk/r/506/data/186) The ontology brainstorm is a working exploration rather than standing doctrine; no future ontology has been chosen and no future data model has been selected.[^\[19\]^](https://app.pensieve.uk/r/506/data/185)[^\[20\]^](https://app.pensieve.uk/r/506/data/189) The open ontology questions are explored in [Product Architecture](./product-architecture/page.md)'s child page, [Ontology Exploration](./product-architecture/ontology-exploration/page.md).
