# Agent Memory

Agent memory is the persistence of an AI agent’s state across sessions, including beliefs, preferences, and learned patterns.^\[1\]^[^data:142] Persistent memory can learn from past mistakes and modify later behavior.^\[2\]^[^data:142] Retrieval-only memory can retrieve semantically similar past interactions, but it cannot learn from them—there is no state update, behavioral change, or pattern recognition across sessions.^\[3\]^[^data:142] The gap between the two approaches is an architecture difference, not a feature difference.^\[4\]^[^data:142] Persistent state is intended to make context compound, with each session adding to rather than resetting the agent’s understanding.^\[5\]^[^data:142]

## PAM’s current persistence model

PAM currently separates project information into two durable substrates.^\[6\]^[^data:186] Structured work and execution state lives in Supabase Postgres.^\[7\]^[^data:186] Rich context lives as files in Supabase Object Storage, primarily in the private `agent-files` bucket.^\[8\]^[^data:186] This file system is PAM’s current equivalent of a persistent context layer.^\[9\]^[^data:186]

The durable file model includes `memory/user.md` for stable information about the person across projects^\[10\]^[^data:186], `memory/memory.md` for durable cross-project facts, rules, constraints, and context^\[11\]^[^data:186], and `project/mind/` for the growing project knowledge layer.^\[12\]^[^data:186] PAM gives the agent filesystem tools to read, search, create, edit, move, and delete authorized files.^\[13\]^[^data:186] On Web, files are hydrated from Object Storage into a temporary Daytona runtime and flushed back to durable storage.^\[14\]^[^data:186] On Desktop, authorized account and project files are synchronized to a local filesystem so the native provider can work with them directly, then changes are published back through PAM’s synchronization system.^\[15\]^[^data:186]

## PAM's three-layer memory model

Claude's ontology-brainstorm analysis reconstructs PAM's memory as three layers. The raw/reference layer holds Sources — uploads and connector pulls — which are not authoritative by default.^\[16\]^[^data:264] The distilled/canonical layer is what Pam reasons from day to day: Project's Core, About Your Human, and Pam's own `map.md`/`playbook.md` notebooks.^\[17\]^[^data:264] Product doctrine calls this "engineered memory" — everything said gets structured underneath the conversation, retrievable but not surfaced by default.^\[18\]^[^data:264] The conversation layer is the threads themselves, ephemeral individually but compressed forward via handoff cards whenever scope changes: when Pam transitions scope or skill, the thread carries a handoff card, a literal compiled summary of everything decided, tagged e.g. "HANDOFF FROM ONBOARDING", passed forward as context, not paraphrased.^\[19\]^[^data:264]

Promotion from the raw layer to the canonical layer is never automatic.^\[20\]^[^data:264] When Pam extracts new facts from an uploaded source, it proposes them rather than folding them in; canonical state changes only on explicit user confirmation.^\[21\]^[^data:264] Uncertainty is recorded rather than forced — the model has a first-class notion of "known-unresolved," not just true/false facts.^\[22\]^[^data:264] Connectors are migrate-once, not continuously reconciled: a connector is read once, reports back, the user confirms, and from then on Pam — not the external tool — is authoritative.^\[23\]^[^data:264] Downstream artifacts regenerate from current state rather than being patched incrementally: the onboarding copy states that PAM rebuilds the next brief using what actually is true now.^\[24\]^[^data:264]

Personalization lives in the canonical layer. About Your Human is a separate per-person profile, distinct from the project notebook, carrying Profile, Working Preferences (cadence, communication style, decision style, check-in frequency), Goals (30–90d outcomes, priorities, success signals), and Constraints (hard constraints, availability).^\[25\]^[^data:264] It is the profile-level counterpart to `memory/user.md` above.

This reconstruction is explicitly flagged as analysis, not a spec: Claude built it from product documentation, one fresh onboarding walkthrough, and one confirmed statement from Amir, not from the codebase, and Amir should correct anything that is wrong about the actual system.^\[26\]^[^data:264] The substrate split above is the confirmed grounding for what PAM stores today, last verified 2026-08-27 from Amir's direct explanation.^\[27\]^[^data:186]

## Storage and update routing

PAM’s current routing rule places clear status, owner, dates, dependencies, or scheduling in a structured database record^\[28\]^[^data:186], while rich explanation, strategy, research, narrative context, history, or generated work goes in a file.^\[29\]^[^data:186] Normal conversation sends a concrete execution change, such as an item starting or finishing, to structured project state^\[30\]^[^data:186], while strategic context, rationale, research, a named person, or a durable lesson updates the appropriate file.^\[31\]^[^data:186] A message may affect both, but PAM is instructed not to duplicate the same truth blindly across both surfaces.^\[32\]^[^data:186]

Foundation learns the stable project shape through conversation, writes the canonical strategic result to `project.md`, and keeps a richer extraction trail in the foundation notebook under `project/mind/`.^\[33\]^[^data:186] Planning reads the foundation and writes Fronts, Milestones, Batches, and Items into Postgres while keeping non-operational rationale and supporting context in files when needed.^\[34\]^[^data:186] Morning Brief, Fulfillment, Project Health, and Reflection read from both substrates.^\[35\]^[^data:186] Structured work, status, dependencies, dates, plans, and allocations come from Postgres^\[36\]^[^data:186], while goals, decisions, assumptions, lessons, research, history, and prior judgments come from files and conversation history.^\[37\]^[^data:186] The agent interprets these together to decide what matters, what changed, what should happen today, and whether the plan is drifting.^\[38\]^[^data:186]

## Retrieval, provenance, and authority

PAM does not currently have one unified ontology or query layer spanning all project knowledge.^\[39\]^[^data:186] Structured records are queried through database tools^\[40\]^[^data:186], while files are navigated and searched through filesystem tools and the project `mind/map.md` convention.^\[41\]^[^data:186] Uploaded documents can also be chunked and indexed for search, with evidence records in Postgres and content in Object Storage.^\[42\]^[^data:186] Conversation history is stored separately and read when recent statements matter.^\[43\]^[^data:186] The agent reconciles these sources at runtime using instructions, tool results, and judgment.^\[44\]^[^data:186]

Provenance is partial: timestamps, creator kind, source metadata, file hashes, message identity, and ingestion/search records are available, but there is not one consistent evidence model that applies to every statement in every substrate.^\[45\]^[^data:186] When sources conflict, current instructions tell PAM to surface the conflict rather than silently pick a winner.^\[46\]^[^data:186] Imported material is reference until the user or an authorized workflow accepts its effect on canonical project truth.^\[47\]^[^data:186]

Across Web and Desktop, Postgres remains authoritative for structured project data^\[48\]^[^data:186], and Object Storage remains the durable cloud source for files.^\[49\]^[^data:186] Desktop keeps an authorized local copy of files for native agent execution and synchronization^\[50\]^[^data:186], while Desktop SQLite is operational state and synchronization bookkeeping, not a second structured project database.^\[51\]^[^data:186]

## The production boundary

Agent memory is a specific sub-problem of the demo-to-production gap; the goldfish problem is one of the named failure modes that separates demos from production.^\[52\]^[^data:142] See [Production Readiness](../production-readiness/page.md) for the broader production boundary. The broader production question appeared across all five clusters: how to take what works in a demo and make it work when real users hit it.^\[53\]^[^data:140] Other named failure surfaces include context bloat under sustained load, concurrent-user state collapse, cost and latency at scale, and state consistency under concurrent access, alongside memory replay gaps.^\[54\]^[^data:144]

Persistence introduces operational costs. True state persistence requires storing, retrieving, and injecting prior context, which consumes tokens.^\[55\]^[^data:142] The cost model of persistent memory at scale is not yet well understood publicly.^\[56\]^[^data:142] Persistent memory can also carry forward bias or errors in training data when it learns from past mistakes.^\[57\]^[^data:142] A system that cannot remember what it did cannot be audited.^\[58\]^[^data:142] These accountability concerns connect to [AI Agent Governance](../ai-agent-governance/page.md).

## Implementation landscape and open decisions

As of June 2026^\[59\]^[^data:142], named implementation references included LangGraph + AgentCore Memory^\[60\]^[^data:142], Oracle enterprise memory systems^\[61\]^[^data:142], and Enterprise Context Graph.^\[62\]^[^data:142] The space has no clear consensus on tooling and remains fragmented.^\[63\]^[^data:142] Open questions include whether a memory layer can work across multi-agent architectures or remains agent-scoped^\[64\]^[^data:142], and whether persistence creates new governance risks, including memory corruption.^\[65\]^[^data:142]

Within PAM, the database/file split is a current implementation choice, not a proven final answer^\[66\]^[^data:186]; the ontology discussion reopens the current boundary without settling it.^\[67\]^[^data:186] PAM has not approved a knowledge graph^\[68\]^[^data:186], an event-sourced redesign^\[69\]^[^data:186], a migration away from the current hierarchy^\[70\]^[^data:186], or a merger of database and file truth.^\[71\]^[^data:186]

[Golden Context](../golden-context/page.md) covers selecting and stewarding reusable context; [AI Agent Governance](../ai-agent-governance/page.md) covers controls and accountability; and [Product Architecture](../../systems/product-architecture/page.md) covers PAM’s broader implementation boundary. This page focuses on the persistence, retrieval, update, and application of agent state.
