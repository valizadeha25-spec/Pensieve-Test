# Agent Memory

Agent memory is how an AI agent retains, retrieves, updates, and applies state across sessions — not just past conversations, but beliefs, preferences, and learned patterns.[^\[1\]^](https://app.pensieve.uk/r/506/data/142) The field splits into two camps. Retrieval-only memory can retrieve semantically similar past interactions but cannot learn from them — no state update, behavioral change, or pattern recognition across sessions.[^\[2\]^](https://app.pensieve.uk/r/506/data/142) True state persistence stores agent state across sessions and modifies behavior based on prior failures, so context compounds: each session adds to rather than resetting the agent's understanding.[^\[3\]^](https://app.pensieve.uk/r/506/data/142) The gap between the camps is an architecture difference, not a feature difference, and retrofitting persistence onto a retrieval-only architecture is not trivial.[^\[4\]^](https://app.pensieve.uk/r/506/data/142)

A practitioner boundary check applies to this vocabulary: Kem Glitch rejects the idea that loosely linked files automatically create knowledge-graph memory — a graph requires explicit modeling and traversal, while a file system can still be an interpretable context-and-routing architecture without making that claim.[^\[5\]^](https://app.pensieve.uk/r/506/data/310) PAM's memory, described below, is file-based.

## PAM's persistence model

PAM separates project information into two durable substrates, last verified 2026-08-27 from Amir's direct explanation at Web commit `cc37dbaa` and Desktop commit `1e9b28d0`.[^\[6\]^](https://app.pensieve.uk/r/506/data/186) Structured work and execution state lives in Supabase Postgres; rich context lives as files in Supabase Object Storage, primarily in the private `agent-files` bucket — the file system is PAM's current equivalent of a persistent context layer, serving the same compounding-context problem as company-brain systems.[^\[7\]^](https://app.pensieve.uk/r/506/data/186)

The durable file model has `memory/user.md` for stable information about the person across projects, `memory/memory.md` for durable cross-project facts, rules, constraints, and context, and `project/mind/` as the growing project knowledge layer: named entities, concepts, research, work products, notebooks, lessons, health artifacts, reflection records, and routine state.[^\[8\]^](https://app.pensieve.uk/r/506/data/186) The agent gets filesystem tools to read, search, create, edit, move, and delete authorized files; on Web, files hydrate from Object Storage into a temporary Daytona runtime and flush back, while on Desktop authorized files synchronize locally for native execution and publish back through PAM's synchronization system.[^\[9\]^](https://app.pensieve.uk/r/506/data/186)

Claude's ontology-brainstorm analysis reconstructs the memory as three layers — explicitly analysis, not a spec, built from product documentation, one onboarding walkthrough, and one confirmed statement from Amir rather than the codebase, which Amir should correct where wrong.[^\[10\]^](https://app.pensieve.uk/r/506/data/264) The raw/reference layer holds uploads and connector pulls, not authoritative by default.[^\[11\]^](https://app.pensieve.uk/r/506/data/264) The canonical layer is what Pam actually reasons from day to day — Project's Core, About Your Human, and Pam's own `map.md`/`playbook.md` notebooks; product doctrine calls this "engineered memory" — everything said gets structured underneath the conversation, retrievable but not surfaced by default.[^\[12\]^](https://app.pensieve.uk/r/506/data/264) The conversation layer is the threads themselves, ephemeral individually but compressed forward via handoff cards whenever scope changes — a literal compiled summary of everything decided, tagged e.g. "HANDOFF FROM ONBOARDING", passed forward as context, not paraphrased.[^\[13\]^](https://app.pensieve.uk/r/506/data/264) Personalization lives in About Your Human, a separate per-person profile distinct from the project notebook, carrying Profile, Working Preferences (cadence, communication style, decision style, check-in frequency), Goals (30–90d outcomes, priorities, success signals), and Constraints (hard constraints, availability).[^\[14\]^](https://app.pensieve.uk/r/506/data/264)

## Update routing and the confirmation gate

Storage routing: clear status, owner, dates, dependencies, or scheduling goes to a structured database record; rich explanation, strategy, research, narrative context, history, or generated work goes to a file.[^\[15\]^](https://app.pensieve.uk/r/506/data/186) In conversation, a concrete execution change such as an item starting or finishing updates structured project state, while strategic context, rationale, research, a named person, or a durable lesson updates the appropriate file; a message may affect both, and PAM is instructed not to duplicate the same truth blindly across both surfaces — routing is enforced mainly through agent instructions and skills, not one universal data abstraction.[^\[16\]^](https://app.pensieve.uk/r/506/data/186) Foundation writes the canonical strategic result to `project.md` with a richer extraction trail in the foundation notebook; Planning reads the foundation and writes Fronts, Milestones, Batches, and Items into Postgres; Morning Brief, Fulfillment, Project Health, and Reflection read both substrates and interpret them together to decide what matters, what changed, what should happen today, and whether the plan is drifting.[^\[17\]^](https://app.pensieve.uk/r/506/data/186)

Promotion from the raw layer to the canonical layer is never automatic: Pam proposes extracted facts, and canonical state changes only on explicit user confirmation — in the observed pitch-deck moment Negin declined, and the deck stayed reference-only with Project's Core untouched.[^\[18\]^](https://app.pensieve.uk/r/506/data/264) Uncertainty is recorded rather than forced — the model has a first-class notion of "known-unresolved," not just true/false facts.[^\[19\]^](https://app.pensieve.uk/r/506/data/264) Connectors are migrate-once, not continuously reconciled: a connector is read once, reports back, the user confirms, and from then on Pam — not the external tool — is authoritative.[^\[20\]^](https://app.pensieve.uk/r/506/data/264) Downstream artifacts regenerate from current state — the onboarding copy states PAM rebuilds the next brief using what actually is true now — flagged as the analysis's lowest-confidence claim since it is inferred from onboarding copy, and simultaneous contradicting inputs are explicitly never tested.[^\[21\]^](https://app.pensieve.uk/r/506/data/264)

## Retrieval, provenance, and authority

PAM does not currently have one unified ontology or query layer spanning all project knowledge: structured records are queried through database tools, files through filesystem tools and the project `mind/map.md` convention, and uploaded documents can be chunked/indexed for search with evidence records in Postgres; conversation history is stored separately and read when recent statements matter, and the agent reconciles these sources at runtime using instructions, tool results, and judgment.[^\[22\]^](https://app.pensieve.uk/r/506/data/186) Provenance is partial — timestamps, creator kind, source metadata, file hashes, message identity, and ingestion/search records — with no consistent evidence model across substrates; on conflict PAM is instructed to surface the conflict rather than silently pick a winner, and imported material is reference until the user or an authorized workflow accepts its effect on canonical project truth.[^\[23\]^](https://app.pensieve.uk/r/506/data/186) Postgres remains authoritative for structured project data and Object Storage remains the durable cloud source for files on both surfaces; Desktop SQLite is operational state, conversations, provider continuity, recovery, and synchronization bookkeeping, not a second structured project database, and structured Desktop actions still call authenticated PAM server tools against the same records used by Web.[^\[24\]^](https://app.pensieve.uk/r/506/data/186)

## Costs, failures, and open decisions

Agent memory is a specific sub-problem of the demo-to-production gap — the goldfish problem is one of the named failure modes that separates demos from production, alongside context bloat under sustained load, concurrent-user state collapse, cost and latency at scale, and state consistency under concurrent access ([Production Readiness](../production-readiness/page.md)).[^\[25\]^](https://app.pensieve.uk/r/506/data/142)[^\[26\]^](https://app.pensieve.uk/r/506/data/144) Persistence consumes tokens — storing, retrieving, and injecting prior context — and the cost model of persistent memory at scale is not yet well understood publicly.[^\[27\]^](https://app.pensieve.uk/r/506/data/142) Learning from past mistakes also means learning from past bias or errors in training data, and a system that cannot remember what it did cannot be audited — the accountability link to [AI Agent Governance](../ai-agent-governance/page.md).[^\[28\]^](https://app.pensieve.uk/r/506/data/142)

As of June 2026 the implementation landscape had no clear consensus on tooling and remained fragmented; named references included LangGraph + AgentCore Memory, Oracle enterprise memory systems, and Woodson Martin's Enterprise Context Graph.[^\[29\]^](https://app.pensieve.uk/r/506/data/142) Open questions include whether a memory layer can work across multi-agent architectures or remains agent-scoped ([Multi-Agent Coordination](../multi-agent-coordination/page.md)).[^\[30\]^](https://app.pensieve.uk/r/506/data/142) Within PAM, the two-substrate split is a current implementation choice, not a proven final answer, chosen before the team had its practical Company Brain experience; the ontology discussion reopens the boundary without settling it, and no knowledge graph, event-sourced redesign, migration away from the current hierarchy, or merger of database and file truth has been approved ([Product Architecture](../../systems/product-architecture/page.md); [Ontology Exploration](../../systems/product-architecture/ontology-exploration/page.md)).[^\[31\]^](https://app.pensieve.uk/r/506/data/186)
